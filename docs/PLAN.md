# court2go — Build Plan (milestones)

Execution plan owned by the build loop. Data layer (Prisma schema/migrations/seed + repositories) and the contract (`packages/types`, `docs/openapi.yaml`) are DONE. Each milestone: build → typecheck → verify → commit.

Legend: ✅ done · 🟡 in progress · ⬜ not started

## M1 — NestJS bootstrap ✅
Bootable API skeleton: deps, `main.ts`, `AppModule`, `PrismaModule`, tenant-context middleware, global exception filter (error envelope), zod validation pipe, `/health`. Verifiable: `GET /health` 200, `GET /` boots, DB connects.

## M2 — Public catalog (read) ✅

## M3 — packages/domain (pricing + grid) ✅
Grid/slot validation, mixed peak/base price breakdown, 30-min lattice expansion, hold TTL. Pure functions, unit-tested. Consumed by availability + bookings.

Shipped as `@repo/domain`: `grid.ts` (`isGridAligned`, `gridStartMinutes`, `maxSlotsFromStart`, `latticeUnitsForBooking`, `expandToLattice`, `validateBookingSelection`), `pricing.ts` (`isPeakAtStart`, `priceForGridUnit`, `computePriceBreakdown` — output satisfies `priceBreakdownSchema`, drop-in for `CreateHoldInput`), `hold.ts` (`computeHoldExpiry`, `isHoldExpired`, `remainingHoldMs`). All types reused from `@repo/types` (no redefinition). Jest wired for the workspace (root `test`/`typecheck` fan-out); the previously-queued `apps/api` `prisma-errors` P2002 classifier spec now runs green (7 tests) — no longer queued. 51 domain unit tests pass incl. the PRD A5.1 AC10 worked example; reviewer clean.

**Carried flag — RESOLVED in M4 (was: schema owner, `packages/types`):** `timeOfDaySchema` permitted a court `openTime` off the :00/:30 lattice (e.g. 08:15), which would push the fixed 30-min lock lattice off-grid (ARCHITECTURE §5.1/§5.4 silent-double-book risk). Closed at BOTH layers during M4 (the availability grid consumes `openTime`): (1) schema — new `latticeAlignedTimeSchema` in `packages/types/src/common/primitives.ts` now constrains `courtScheduleDaySchema` open/close to minute ∈ {:00,:30} (`24:00` still valid for close); `timeOfDaySchema` itself left unconstrained so peak-range boundaries are unaffected; (2) data — new migration `20260726135123_court_schedule_day_lattice_align_check` adds a CHECK (`open_time`/`close_time ~ ':(00|30)$'`), applied + live-verified (08:15 rejected, 08:30/24:00 accepted). `validateBookingSelection`'s `OFF_LATTICE` guard remains as defense-in-depth. Seed (08:00/22:00) already compliant.

## M4 — Availability ✅
`courts/{courtId}/availability?date=YYYY-MM-DD` — per-court free/taken start-time grid. Read-only, tenant-header-scoped (public, no member session).

Shipped in `apps/api` as `AvailabilityModule` (controller + service + the three RLS-scoped repositories provided locally): resolves the court (404 mirrors `CatalogController.getCourt` — inactive/soft-deleted never leaks), reads the queried weekday's schedule (closed day → `{closed:true, starts:[]}`), then builds the grid off `@repo/domain` (`gridStartMinutes`/`maxSlotsFromStart`/`computePriceBreakdown` — no reimplementation). Occupancy = active `booking_slot` rows (`bookings.findActiveSlots`) ∪ maintenance blocks (`courts.listBlocksInRange`) ∪ min-lead-time (PRD C1.2 AC2) ∪ max-advance-window (AC3); `maxSlotCount` per grid start is the largest contiguous run whose every 30-min lattice unit is free (AC4 — cannot cross an occupied/blocked unit). `pricePerSlotCount[k-1]` = server-computed base/peak-summed total for a k-slot booking (preview aid; authoritative price re-derived at hold time in M6). Timezone: ICT=UTC+7 fixed (no tz stored; Thailand-only MVP, PRD NFR9) — `ictLocalToUtc` handles `24:00`; weekday resolved via UTC (host-tz independent). 11 new availability unit tests (68 api total) + 51 domain, all green; tsc clean; reviewer clean.

Deferred (🟢 nits, both pre-existing platform-wide patterns, NOT introduced by M4): (1) `courtId` path param has no UUID pipe — a malformed id can surface a Postgres 500 instead of a clean 404 (same as `CatalogController.getCourt`; fix platform-wide or neither); (2) `isoDateSchema` is regex-only so a calendar-invalid date (e.g. `2026-02-30`) is silently normalized by `Date.UTC` — tighten the shared primitive if strictness is wanted. Neither gates M4.

## M5 — Member auth (OTP stub + LINE) ✅
`auth/otp/request|verify` (OtpSender stub), LINE login-url/callback, session cookie, `me` profile, one-time phone bind. Phone-verified-once invariant.

Shipped in `apps/api`: a hexagonal `IntegrationsModule` (`@Global`) binding `OTP_SENDER`/`LINE_CLIENT` ports to env-selected adapters — `StubSmsAdapter` (logs the code) and `StubLineAdapter` (deterministic `lineUserId` from the auth code) — so real SMS/LINE providers drop in as one factory `case` with no consumer change. `AuthMemberService` orchestrates: HMAC-SHA256-hashed OTP (never plaintext, constant-time compare, crypto-random 6-digit), per-challenge attempt cap + Tenant-configurable resend cooldown & rolling-hour send cap, HMAC-signed tenant-bound LINE `state` (forgery/cross-tenant rejected), and a DB-backed `ClientSession` → `httpOnly` `c2g_member_session` cookie. LOGIN auto-provisions/verifies a Member; BIND enforces challenge-owner match + PHONE-VERIFIED-ONCE (`DUPLICATE_MEMBER` conflict). `MeController` GET/PATCH (phone immutable — changes go via OTP BIND). Tenant isolation rides `withTenant()`/RLS on every read/write. 57 api unit tests pass (+2 from review); tsc clean.

Reviewer findings addressed: (1) added `@HttpCode(200)` to the four `@Post` auth handlers (NestJS defaulted to 201, drifting from openapi's 200); (2) OTP `devCode` disclosure and the cookie `Secure` flag now gate on an explicit dev/test allow-list (`isDevLikeEnv`) — **fail-closed** so an unset `NODE_ENV` in prod never leaks codes or drops `Secure` (dev ergonomics preserved via `NODE_ENV=development` in `start:dev`); (3) blocked Members (`isBlocked`) are now rejected at every session-mint path (OTP + LINE) with `MEMBER_BLOCKED`/403, defense-in-depth for the admin-block invariant. Deferred (🟢, both stub-only): LINE `state` carries no issued-at/expiry (no replay window — revisit with the real LINE adapter); cookie `sameSite:'lax'` assumes web+api share a registrable domain — if prod splits them cross-site, switch to `SameSite=None; Secure` (M11 deploy/topology decision).

## M6 — Booking + hold lifecycle ✅
Shipped in `apps/api` as `BookingsModule` (three member-guarded controllers + `BookingService` + repositories provided locally, mirroring M5). `POST courts/{id}/holds` re-validates the selection server-side (`@repo/domain` `validateBookingSelection` incl. the 30-min `OFF_LATTICE` guard + lead-time/advance-window/blocks defense-in-depth), re-derives the AUTHORITATIVE price via `computePriceBreakdown` (client-sent price never trusted), then opens the Hold through the safety-critical `BookingsRepository.createHold` (the `uniq_active_court_slot` partial index is the ultimate double-book guard; `SlotUnavailableError`→409). Verification fork on `member.phoneVerified`: unverified → stays `PENDING_VERIFICATION` (`nextStep=VERIFY_PHONE`); verified → advances in ONE transaction (`advanceOutOfVerification`, the SOLE code path to `CONFIRMED` since there is no DB convergence trigger) to `PENDING_PAYMENT`+`AWAITING_SLIP_UPLOAD` (QR) or `CONFIRMED`+`PAY_ONSITE_NOT_COLLECTED` (Pay-Onsite, redeeming any promo). `GET bookings/{id}` lazily self-heals a `PENDING_VERIFICATION` booking on read once OTP completes (or to `EXPIRED` if the hold lapsed); ownership fails closed to 404 (no existence leak). Promo apply/remove re-price off the booking's SNAPSHOT (never live court config); `resolvePromotion` enforces scope + caps, and total-cap redemption is atomic (single-statement `UPDATE … WHERE total_uses < max_total_uses`, `PromotionCapReachedError`→409) — redemption counted only at CONFIRMED. Self-service `cancellation-request` (Confirmed + before the 2h cutoff, slots NOT released until admin approve in M9). `GET me/bookings` paginated with upcoming/past/all scope. Background `HoldExpiryJob` sweeps expired holds every 15s under a `pg_try_advisory_lock` singleton guard (interactive-tx budget raised so a multi-tenant sweep can't abort mid-flight and leak the lock). Every status change writes an audit row. Carried M6 lattice-alignment flag confirmed already discharged (migration `court_schedule_day_lattice_align_check` + `latticeAlignedTimeSchema` mirror). 58 new unit tests (126 api total) + 51 domain, all green; tsc clean; reviewer clean (no blockers; 4 SHOULD-FIX + NITs all applied). QR PromptPay payload, slip upload, and admin confirm/reject deferred to M7; admin actions to M9.

## M7 — Payments ✅
Pay-Onsite auto-confirm; QR: dynamic PromptPay EMVCo payload, slip upload-url + slip submit, admin confirm/reject. Payment status machine.

**No data/contract work:** schema already carries `Payment.qrPayload`/`slipObjectKey`/`slipUploadedAt`/review fields + `Branch.promptPayId` (prisma-data pre-built); all endpoints + DTOs (`Payment`, `PromptPayQr`, `SlipUploadUrl*`, `ConfirmSlipBody`, `AdminConfirm/RejectPaymentBody`, `SlipViewUrlResponse`) already in `openapi.yaml`/`packages/types`. Bind to them, no api-designer/prisma-data.

**Scope decisions (tech lead):**
- **Pay-Onsite auto-confirm is already shipped** by M6 `advanceOutOfVerification` (PENDING_VERIFICATION→CONFIRMED, Payment `PAY_ONSITE_NOT_COLLECTED`, promo redeemed). M7 verifies + covers it with tests, does NOT re-implement.
- **CONFIRMED-write invariant, reconciled:** `advanceOutOfVerification` only covers transitions OUT of PENDING_VERIFICATION. Admin slip-confirm (PENDING_PAYMENT_CONFIRMATION|PENDING_PAYMENT → CONFIRMED) is a *distinct* transition, so M7 adds a second authoritative transaction `BookingsRepository.confirmPayment(...)` living in the SAME repository alongside `advanceOutOfVerification` — booking status + payment row + promo-redeem atomic, status-guarded, mirroring its structure (no parallel writer in PaymentsRepository). QR-branch promo redemption is counted HERE (deferred to CONFIRMED, per M6 note). `rejectPayment(...)` is the atomic reject analog (Booking→REJECTED releases slots + Payment→REJECTED, one tx).
- **Admin HTTP endpoints deferred, logic built now:** M8 owns admin auth+RBAC (only `AdminSessionsRepository` stub exists, no guard). Shipping an unguarded money-mutating `/admin/**` POST is unacceptable, so the admin confirm/reject/slip-url *service methods + authoritative transactions* are built and unit-tested at the service layer in M7; the thin `/admin/bookings/{id}/payment/**` HTTP controllers + RBAC guard land with M8/M9. **Carryover → M8/M9.**

**Build slices:**
1. `@repo/domain/promptpay.ts` — pure EMVCo Merchant-Presented payload + CRC16-CCITT, tested against published Thai PromptPay test vectors.
2. `apps/api/integrations` — `ObjectStorage` port + local stub adapter (deterministic presigned PUT / signed GET, no real S3 for MVP), `PromptPayQrService` port + `PromptPayAdapter` (domain builder + `qrcode` → data URL); bound in `IntegrationsModule`.
3. `apps/api/modules/payments` — `PaymentService` + `PaymentsModule` + client `PaymentController`: GET `/bookings/{id}/payment` (QR generated for QR branch), POST `slip-upload-url`, POST `slip` (→ PENDING_PAYMENT_CONFIRMATION). Payment status machine enforced (illegal transition → 409 INVALID_STATE_TRANSITION).
4. `BookingsRepository.confirmPayment/rejectPayment` + `PaymentService` admin methods (`adminConfirmPayment`, `adminRejectPayment`, `issueSlipViewUrl`) — unit-tested at service level.

**Shipped:** all four slices above. `confirmPayment` is the second authoritative CONFIRMED writer (alongside `advanceOutOfVerification`, same repository) — one status-guarded `withTenant` tx: Booking [PENDING_PAYMENT|PENDING_PAYMENT_CONFIRMATION]→CONFIRMED, promo redeem via shared `redeemPromotionWithTx` (QR redemption counted HERE, at confirm), Payment→CONFIRMED. `rejectPayment` atomically REJECTs + releases slots. Pay-Onsite auto-confirm verified untouched (M6). Payment status machine enforced via `PAYMENT_TRANSITIONS` (Pay-Onsite terminal → structurally unconfirmable). PromptPay builder pinned to CRC-16/CCITT-FALSE catalogue check (`29B1`). Reviewer: no blockers; 3 SHOULD-FIX applied (client `objectKey` prefix-validated against the server-issued tenant+booking key; `contentLength` capped at 10 MB; dead non-atomic `PaymentsRepository` writers + stale doc removed → read-only repo) + 2 nits (submitSlip payment-count guard; confirm clears `rejectionReason`). Tests: api 151 (was 126), domain 70 (was 51), both typecheck clean.

**Carryovers → M8/M9:** (1) admin HTTP endpoints `POST /admin/bookings/{id}/payment/{confirm,reject}` + `GET .../slip-url` are NOT wired — the service methods + authoritative transactions exist and are unit-tested, but the controllers must land behind M8's `AdminSessionGuard` + `RolesGuard` (Owner/Admin/Branch-Admin) with branch-scope enforcement; a `// TODO(M8/M9)` marks the spot in `payment.service.ts`. (2) 🟢 nit deferred: pin one externally-published PromptPay end-to-end QR vector (current spec relies on the CRC catalogue check + structural/round-trip invariants + hand-derived vectors, which the build agent flagged). (3) `LocalObjectStorageAdapter` is an MVP stub — real S3/R2 `S3Adapter` binding is an M11 deploy concern (the `contentLength` cap + private tenant-prefixed keys are already enforced in `PaymentService`).
